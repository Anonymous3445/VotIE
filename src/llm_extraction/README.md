# LLM Span Extraction

Clean architecture for LLM-based span extraction using Outlines with post-processing alignment.

## Architecture

### Two-Stage Approach

**Stage 1: LLM Generation (Text + Type Only)**
- Model generates only `text` and `type` fields
- Uses Outlines to constrain output to valid JSON schema
- No positions generated (prevents truncation issues)

**Stage 2: Post-Processing Alignment**
- Find exact positions of generated text in source document
- Add `start` and `end` fields via string matching
- Validate alignment fidelity (exact character match)

This follows the Gemini approach and prevents issues with models truncating text to fit position constraints within token limits.

## How It Works

### 1. Schema Design (`schemas.py`)

```python
class SpanEntity(BaseModel):
    text: str                     # Generated by LLM
    type: str                     # Generated by LLM
    start: Optional[int] = None   # Added by alignment
    end: Optional[int] = None     # Added by alignment

    class Config:
        # Custom schema for LLM excludes start/end
        json_schema_extra = {
            "properties": {
                "text": {...},
                "type": {...}
            },
            "required": ["text", "type"]
        }
```

The Pydantic model has all 4 fields internally, but the JSON schema exposed to the LLM only has `text` and `type`.

### 2. Generation (`extractor.py`)

```python
# Generate with Outlines (text + type only)
output = self.generator(
    prompt,
    max_tokens=1024,
    temperature=0.1
)

# Convert to entities (positions are None)
entities = [
    SpanEntity(
        text=entity.text,
        type=entity.type,
        start=None,  # Will be filled by alignment
        end=None
    )
    for entity in output.entities
]
```

### 3. Alignment (`span_alignment.py`)

```python
# Find exact positions in source text
result, stats = align_extraction_result(result, strict=True)

# For each entity:
#   - Find exact text match in source
#   - Add start/end positions
#   - Validate character-for-character match
#   - Report alignment fidelity
```

## Benefits

1. **No Truncation**: Model doesn't truncate text to fit position constraints
2. **Exact Matches**: Post-processing ensures character-level precision
3. **Outlines Constraints**: Still validates JSON structure and entity types
4. **Alignment Metrics**: Track fidelity of text extraction
5. **Clean Architecture**: Separation of concerns (generation vs alignment)

## Usage

```python
from src.llm_extraction.llama.extractor import LLaMASpanExtractor
from src.llm_extraction.llama.config import LLaMAConfig

# Create extractor
config = LLaMAConfig(
    model_id="meta-llama/Llama-3.2-3B-Instruct",
    temperature=0.1,
    max_tokens=1024
)
extractor = LLaMASpanExtractor(config=config, strategy="few_shot")

# Load few-shot examples
from src.llm_extraction.few_shot_selector import load_and_format_few_shot_examples
examples = load_and_format_few_shot_examples("data/citilink_spans/train.jsonl", num_examples=5)
extractor.load_few_shot_examples(examples)

# Extract
result = extractor.extract(
    text="O Executivo Municipal deliberou por unanimidade...",
    document_id="doc_001",
    align_spans=True  # Add positions via alignment
)

# Check results
print(f"Extracted {len(result.entities)} entities")
for entity in result.entities:
    print(f"  - {entity.text} ({entity.type}) [{entity.start}:{entity.end}]")
```

## Schema Flow

```
LLM Input (Outlines Schema):
{
  "entities": [
    {"text": "...", "type": "..."},  # Only these fields visible to LLM
    ...
  ]
}

↓ Generation

LLM Output:
{
  "entities": [
    {"text": "o Executivo Municipal", "type": "VOTER-FAVOR"}
  ]
}

↓ Alignment Post-Processing

Final Result:
{
  "entities": [
    {
      "text": "o Executivo Municipal",
      "type": "VOTER-FAVOR",
      "start": 29,  # Added by alignment
      "end": 50     # Added by alignment
    }
  ]
}
```

## Comparison: Before vs After

### Before (Position Generation)
- Model generates: `{"text": "...", "type": "...", "start": X, "end": Y}`
- Problem: Model truncates text to fit all 4 fields within token budget
- Result: "Conceição" → "Concei" (truncated at accent)

### After (Post-Processing Alignment)
- Model generates: `{"text": "...", "type": "..."}`
- Alignment adds: `start` and `end` via exact string matching
- Result: "Conceição" → "Conceição" (complete, no truncation)

## Portuguese Character Support

Outlines handles Portuguese characters correctly. The truncation issue was NOT due to UTF-8 encoding, but due to schema complexity (4 fields vs 2 fields).

Supported characters: á, é, í, ó, ú, ã, õ, ç, Ç, etc.
